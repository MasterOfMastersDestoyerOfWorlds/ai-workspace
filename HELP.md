# ixd help

Generated by `ixd docs`; every word below comes from a command's docstring and signature.

```
usage: ixd [-h] command ...

Workspace commands: worktrees, landing, machine setup and transcript statistics.

positional arguments:
  command
    docs      Write the command reference into README.md and HELP.md from the
              docstrings.
    land      Merge a worktree's change into the main branch and clean up
              after it.
    ninfer    Start ninfer in the Windows box's WSL distro and make sure pi's
              models.json points at it.
    review    Open a ticket's page in the browser and its worktree in VS Code,
              or pick one in REVIEW.
    setup     Clone the repositories, install the commands, record REPO_HOME,
              install the autofix artifact.
    ssh       setup
    stats     Print wall time by activity, thinking pauses, slow calls, errors
              and repeated command shapes.
    wt        abort, archive, commit, continue, done, launch-add, launch-list,
              new, stage-moves, status, sync

options:
  -h, --help  show this help message and exit
```
## ixd docs
```
usage: ixd docs [-h] [--check]

Write the command reference into README.md and HELP.md from the docstrings.

README.md gets a table and one section per command, between the generated-region markers, so the
prose around it survives. HELP.md gets every parser's help exactly as a terminal prints it. Both
come from the same decorators the CLI itself is built from, so neither can drift.

options:
  -h, --help  show this help message and exit
  --check     report whether the files are current and change nothing, exiting
              1 when they are stale
```
## ixd land
```
usage: ixd land [-h] [-m MESSAGE] [--body {none,changes,description}]
                [--keep-launch] [--keep-worktree] [--no-build] [--no-mark]
                [worktree_name]

Merge a worktree's change into the main branch and clean up after it.

Six steps, each refusing to continue on failure. Replay the change onto the current main branch.
Remove every .vscode/launch.json entry named after a ticket (``PATCH-117: quad-layout``), the
F5 verification aids ``wt launch-add`` writes, while other launch.json changes, such as a new
scene's entry, land. Squash the diff into one commit. Fast-forward the main checkout. Remove
the worktree and its branch. Mark the branch's ticket DONE, which happens after the removal so
the ticket CLI's unmerged-worktree guard sees the landed state.

Before the removal, a VS Code window that shows the worktree is switched to the main checkout
with ``code -r``, so its Java extension stops writing into the directory being deleted; this
waits until the very end when land itself runs in that window's terminal, which the switch
would close. ``code -r`` is used only when it will reach that window (the only window, or the
last active one); otherwise the output says which window to switch. Whatever the extension
wrote back meanwhile is cleared once more after the rebuild.

If git cannot delete the folder because the editor keeps writing into it, the land goes on:
git's record of the worktree is dropped, and the branch, the DONE mark and the rebuild still
happen; the folder is cleared at the end.

Run on a folder git no longer has a worktree for (already landed, but an editor kept writing
into it, or the shell still sits in the deleted directory), it finishes the cleanup: a branch
already in the main branch is deleted, its ticket marked DONE, VS Code moved off, folder deleted.

A sync that stopped on conflicts is finished here when the markers are gone, so resolving the
files and running this one command is the whole recovery; it refuses, naming the files, while
any marker remains.

The main checkout is then recompiled: the VS Code Java extension does not notice files git
changed underneath it, so the next F5 would otherwise run pre-merge classes and answer HTTP 404
for routes that now exist.

positional arguments:
  worktree_name         worktree path or bare name, defaulting to the one
                        holding the current directory

options:
  -h, --help            show this help message and exit
  -m MESSAGE, --message MESSAGE
                        override the commit message entirely, instead of
                        building it from the ticket
  --body {none,changes,description}
                        commit body: the subject alone, the ticket's changes-
                        made bullets, or its description
  --keep-launch         keep the ticket-named launch.json entries instead of
                        removing them
  --keep-worktree       merge but leave the worktree and branch in place
  --no-build            skip recompiling the main checkout after the merge
  --no-mark             leave the ticket's status alone instead of marking it
                        DONE
```
## ixd ninfer
```
usage: ixd ninfer [-h] [--host HOST] [--port PORT] [--user USER] [--wait WAIT]
                  [--root ROOT] [--model MODEL] [--flags FLAGS] [--stop]
                  [--check]

Start ninfer in the Windows box's WSL distro and make sure pi's models.json points at it.

Checks the tailnet, starts the server when it is not already answering, refreshes the Windows
port proxy onto the distro's current address, waits for the weights to load, then writes the
provider into pi's models.json if it is missing or stale. Safe to rerun: a server that is
already up is left alone, and the proxy is repointed either way.

options:
  -h, --help     show this help message and exit
  --host HOST    the Windows box's tailnet name
  --port PORT    the port ninfer-serve listens on
  --user USER    ssh user, when it differs from this machine's
  --wait WAIT    seconds to wait for the weights to load before giving up
  --root ROOT    the ninfer checkout inside WSL, instead of the one ninfer-
                 start.sh holds
  --model MODEL  the model file under that checkout, instead of the one
                 ninfer-start.sh holds
  --flags FLAGS  ninfer-serve flags, instead of the ones ninfer-start.sh holds
  --stop         stop the server instead, giving the GPU back
  --check        report the state without starting anything
```
## ixd review
```
usage: ixd review [-h] [--no-editor] [--page-only] [ticket]

Open a ticket's page in the browser and its worktree in VS Code, or pick one in REVIEW.

The page answers why, what, where and how fast before any diff is opened, in this order:

- Open decisions: the ticket's unresolved ``unknowns``, in a highlighted box.
- Context: the ticket's ``review-summary`` (what changed and why it is needed, at most 50
  words in 3 sentences, which ``generate_board.py`` enforces; set with ``generate_board.py update ID
  --review-summary @FILE``; a highlighted box says so when it is missing), the repo-plan phase
  the description names, the branch this worktree is stacked on and the open tickets stacked
  on it (links to their review pages), blocked-by / blocks, and the rulings paragraph.
- Boundaries that changed: .java classes added, deleted and moved (old -> new package), and
  public/protected declarations the diff adds or removes. The diff runs from the change's
  start (the stack fork, or the merge base with its base branch) to the working tree,
  untracked files included, as ``stage-moves`` reads it.
- Files to read first: ranked by changed lines that are not mechanical (``stage-moves``'
  rules: renames, imports naming a moved class, comment-only Java files), each a VS Code link
  opening the file at its first real hunk; mechanical-only and deleted files listed apart.
- Measurements: ``tmp/<ticket-lowercase>-measurements.json`` in the worktree, as a
  before/after table with percent change, regressions highlighted. The schema::

      {"measurements": [{"suite": "quad-suite", "item": "buddha", "metric": "seamless",
                         "unit": "ms", "before": 3520, "after": 3384,
                         "lower_is_better": true, "note": "median of 4"}],
       "tests": {"command": "mvn test", "run": 538, "failed": 0},
       "tolerance_percent": 0, "notes": "how and where it was measured"}

  ``before``/``after`` are numbers, or strings (fingerprints) compared for equality;
  ``lower_is_better`` is true, false, or null for a value with no better direction; a
  change the wrong way by more than ``tolerance_percent`` is a regression. ``tests`` may be
  a list. A bare list is read as ``measurements``.
- Verification: the F5 launch entry, the test counts from the measurements file and the
  screenshots under ``tmp/`` as thumbnails.
- Definition of done and todos; then, collapsed, the worktree (branch, uncommitted files, last
  agent note), changes made, the raw description, testing plan, related files and the JSON.

A ticket with no worktree still renders, without the sections read from the diff and tmp/.
The page is written to ``~/.cache/ixd/review/<ID>.html`` and carries buttons that open the
worktree and the ticket JSON in VS Code. The worktree is opened with ``code <folder>``, which
focuses the window already showing it and opens a new one otherwise.

Under Hyprland the page opens in a browser window of its own on the first empty workspace
right of every workspace in use, VS Code goes on the one after it (a window already showing
the worktree is moved there, not duplicated), and the view switches to the page.

With no ticket, every ticket in the REVIEW state is listed with its description and a score in
brackets, the number of open tickets that depend on it directly or through a chain, highest
score first; move with
the up and down arrows (or k and j) or type an entry's number, then press enter to open it.

positional arguments:
  ticket       ticket id such as ``craw-29``; omit it to choose from the
               tickets in REVIEW

options:
  -h, --help   show this help message and exit
  --no-editor  open only the page, leaving VS Code alone
  --page-only  write the page and print its path; open no browser or editor,
               move no window
```
## ixd setup
```
usage: ixd setup [-h] [--repo-home REPO_HOME] [--dry-run] [--no-shell]
                 [--no-tools] [--no-maven]

Clone the repositories, install the commands, record REPO_HOME, install the autofix artifact.

Every step is idempotent, so rerunning after a partial failure is safe. REPO_HOME defaults to the
directory holding this checkout, because the other repositories are its siblings. It is written to
.claude/settings.local.json for Claude sessions and to the shell profile for terminals.

options:
  -h, --help            show this help message and exit
  --repo-home REPO_HOME
                        where the repositories live, defaulting to the parent
                        of this checkout
  --dry-run             print every step without running it
  --no-shell            do not touch the shell profile or the user environment
  --no-tools            skip installing the commands and syncing the
                        environment
  --no-maven            skip installing the autofix artifact into ~/.m2
```

### ixd ssh setup
```
usage: ixd ssh setup [-h] [--user USER] [--key KEY] [--out OUT] [--encoded]
                     [--force]
                     [host]

Send the Windows-side OpenSSH setup script to a peer, keyed to this machine, and test it.

Tries the connection first: when it already works there is nothing to send. Otherwise this
machine's public key is read (a missing ed25519 pair is created), ssh-setup.ps1 is written out
with a call that passes it that key, and Taildrop carries it over. The script installs the
server, authorises the key in whichever file that account's sshd actually reads, and narrows
port 22 to the tailnet. Only running it stays manual, since nothing can reach the box until it
has.

positional arguments:
  host         the peer's tailnet name

options:
  -h, --help   show this help message and exit
  --user USER  ssh user, when it differs from this machine's
  --key KEY    private key to authorise, when it is not the default ed25519
               one
  --out OUT    where to write the script, instead of the cache directory
  --encoded    print a one-line paste that carries the script instead of
               sending a file
  --force      send it even when the connection already works
```

### ixd wt archive
```
usage: ixd wt archive [-h] -r REASON [-m MESSAGE] [--keep-worktree]
                      [--no-mark]
                      [worktree_name]

Commit a worktree's change, tag it archive/<name>, remove the worktree, mark the ticket ARCHIVED.

For an experiment that is not going to land: the work stays reachable as one commit on the
tag, with the reason in the tag message and on the ticket, and nothing of it reaches the main
branch. The diff is committed where it sits, on whatever main-branch commit the worktree was
last synced to; there is no rebase, because replaying dead work onto today's main branch is
conflict resolution for nothing. The launch.json entries stay in the commit as part of the
record.

Refuses when the branch has nothing to archive (no diff and no commits of its own) or when the
tag already exists. Recover the work later with ``git worktree add <path> archive/<name>``.

positional arguments:
  worktree_name         worktree path or bare name, defaulting to the one
                        holding the current directory

options:
  -h, --help            show this help message and exit
  -r REASON, --reason REASON
                        why the work is being shelved rather than landed; goes
                        on the tag and the ticket
  -m MESSAGE, --message MESSAGE
                        override the commit subject, instead of ``<TICKET>:
                        <title> (archived)``
  --keep-worktree       tag and mark, but leave the worktree and branch in
                        place
  --no-mark             leave the ticket's status alone instead of marking it
                        ARCHIVED
```

### ixd wt done
```
usage: ixd wt done [-h] [worktree_name]

Sync, refuse leftover diagnostics, build, run the launch entry, check tmp/, mark REVIEW.

Log lines, public counters, describe/dump helpers, sample limits and ``*Probe.java`` files
the diff adds are refused unless the ticket's definition of done names them: strip them, or
name them there when they are meant to land. Every step must pass. A failure stops with the reason and nothing is marked, because a ticket in
REVIEW is a claim that the user can verify the work with F5. The launch entry is run exactly as
F5 runs it, only headless, so a crash on that path is caught here and never at the user's
keyboard; there is no way to skip it.

After the build, each module's Maven classes are copied over the IDE's ``target-ide/``
output, which is what F5 actually runs: VS Code's Java extension may not have rebuilt after
the agent's edits, and would otherwise launch stale classes without a word.

positional arguments:
  worktree_name  worktree path or bare name, defaulting to the one holding the
                 current directory

options:
  -h, --help     show this help message and exit
```

### ixd wt new
```
usage: ixd wt new [-h] [--repo {Ixdar,ixdar-tickets,ai-workspace}]
                  [--base BASE]
                  ticket

Create the worktree and branch off the main branch, seed it, and print the agent brief.

The branch takes the ticket's name, which is how `ixd wt done` and `ixd land` find the ticket to
mark. The virtualenv is created up front so an agent's first command is not a cold install. The
brief that is printed is everything an agent needs to start: the paths, the ticket file, the
verbs, and what is denied.

With ``--base`` the worktree is stacked on another worktree's branch instead: it starts from that
branch's tip, and `sync`, `commit` and `done` replay onto the base rather than the main branch,
so its diff is only its own change. The base's change must be committed (`ixd wt commit`) for
the stacked worktree to see it. Once the base lands and its branch is gone, the stacked worktree
replays onto the main branch again; `ixd land` refuses it while the base is still unlanded.

positional arguments:
  ticket                worktree and branch name, usually the ticket id such
                        as craw-27

options:
  -h, --help            show this help message and exit
  --repo {Ixdar,ixdar-tickets,ai-workspace}
                        repository under REPO_HOME that gets the worktree
  --base BASE           stack on this worktree branch instead of the main
                        branch
```
### ixd wt stage-moves
```
usage: ixd wt stage-moves [-h] [worktree_name]

Uncommit the change, stage its move hunks, and leave every code hunk unstaged for review.

A package move touches hundreds of files with nothing but a moved path, a ``package`` line
and ``import`` lines, which buries the few hunks that change code. This puts the change back
in the working tree (undoing ``wt commit``, never anything below the worktree's own base) and
stages exactly the mechanical part: renames, plus hunks whose changed lines are all
``package``/``import`` lines or blank and whose imports name a class the change moves, plus
the whole of every Java file whose changes are only comments, blank lines or such imports. An
import change that names no moved class belongs to the code beside it, and so does a comment
change in a file that also changes code. ``git diff --cached`` then shows the mechanical part
and ``git diff`` (with untracked new files) shows the code to read.

A worktree stacked on this one keeps working: its history still holds this change's commit,
and ``sync`` refuses to replay it until this worktree is committed again or landed.

positional arguments:
  worktree_name  worktree path or bare name, defaulting to the one holding the
                 current directory

options:
  -h, --help     show this help message and exit
```
### ixd wt status
```
usage: ixd wt status [-h] [worktree_name]

Show the branch, its refs, the changed files, added diagnostics, and the last agent note.

This is what a relaunched agent reads instead of a hand-written brief. The note is the closing
prose of the transcript whose tool calls actually worked in this worktree, so an agent picking
the work up learns what was built and what was left. Refs are the published and archived
copies of the branch (``origin/<branch>``, ``archive/<branch>``), so nobody reaches for the
denied ``git branch`` or ``git tag`` to find them. Diagnostics are the log lines, counters and
probes ``wt done`` refuses unless the ticket's definition of done names them.

positional arguments:
  worktree_name  worktree path or bare name, defaulting to the one holding the
                 current directory

options:
  -h, --help     show this help message and exit
```
### ixd wt sync
```
usage: ixd wt sync [-h] [--base BASE] [worktree_name]

Rebase the uncommitted change onto the main branch and leave it uncommitted again.

Work is never lost: the change is parked in a temporary commit, replayed, then unpacked. A real
conflict leaves the rebase in progress with the files listed, for `continue` or `abort`.

A worktree stacked with ``wt new --base`` replays onto its base branch instead. ``--base``
stacks an existing worktree the same way: only its own change moves onto the base's tip, and
later syncs keep it there until the base lands.

Afterwards the tree is compiled and Maven's classes are copied over the IDE's ``target-ide/``,
also when it was already on top of the main branch: VS Code compiles the annotation registries
Maven generates rather than generating its own, and its own build can lag the latest edits, so
without this F5 runs registries missing whatever master added, or classes older than the
source. A failed build leaves the sync in place and exits 1.

positional arguments:
  worktree_name  worktree path or bare name, defaulting to the one holding the
                 current directory

options:
  -h, --help     show this help message and exit
  --base BASE    stack this worktree on that worktree branch from now on
```
